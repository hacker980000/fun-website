# Typing Core v2 Stage 23 - Real Device Evidence & Baseline

Date: 2026-09-21
Baseline: Typing Core v2 Stage 22

## Purpose

Stage 23 is an evidence stage, not a feature stage. It keeps the Stage 22 typing/autocorrect implementation unchanged and adds a repeatable device-validation layer so later tuning can be based on measured Android behavior instead of guessed thresholds.

The Stage 22 device chain remains mandatory. Stage 23 wraps it and then collects repeated cold/warm launch, first-suggestion, process-survival, memory and frame-timing evidence on the exact APK under test.

## Hard gates

A Stage 23 run fails when any of these occur:

- the full Stage 22 validation chain fails;
- the controlled offline `thank -> you` next-word fixture is missing;
- the IME process dies during a round or warm relaunch;
- a required privacy-safe cold-start milestone is absent;
- a `FATAL EXCEPTION` or `ANR in` marker appears.

Stage 23 deliberately does **not** hard-gate a latency, PSS-memory, or frame-jank budget. Those values are baseline evidence. Stage 24 may introduce evidence-backed tuning only after API/device results have been compared.

## Evidence collected per run

`stage23_ci_real_device_baseline.sh` defaults to five rounds (configurable from 3 to 20 with `STAGE23_ROUNDS`). Each round records:

- Android `am start -W` cold and warm timings (`ThisTime`, `TotalTime`, `WaitTime` when the platform reports them);
- the existing Stage 21 privacy-safe milestones: `learning_models_ready`, `service_ready`, `first_input_view_ready`, `first_suggestion_ready`;
- `dumpsys meminfo` for total PSS evidence;
- `dumpsys gfxinfo ... framestats` raw frame evidence plus parser-derived 16.7 ms / 33.3 ms proxy counts;
- process PID survival;
- logcat for crash/ANR and fixed Stage 21 diagnostic markers;
- non-identifying device characteristics needed to interpret results: API level, Android release, manufacturer/model, product, ABI, emulator flag and build type.

The script does not intentionally collect ADB serial numbers, account identifiers, clipboard contents, conversation content, editor text, or user-app context. The only typed fixture is fixed CI text generated by the script itself.

## Machine-readable outputs

The report directory contains:

- `device.properties` - non-account device/build metadata;
- `round-N-cold-am-start.txt` / `round-N-warm-am-start.txt`;
- `round-N-meminfo.txt`;
- `round-N-gfxinfo.txt`;
- `round-N-logcat.txt`;
- `baseline-metrics.csv` - one normalized row per round;
- `baseline-summary.json` - aggregate medians/maxima and frame proxy totals;
- `baseline-summary.txt` - compact human-readable aggregate;
- `summary.txt` - Stage 23 hard-gate result.

`stage23_merge_device_evidence.py` merges multiple `baseline-summary.json` files into `stage23-device-matrix.csv/json` without declaring a device winner or inventing a pass threshold.

## GitHub Actions coverage

The canonical Android workflow uses the Stage 23 wrapper for:

- automatic API 36 emulator smoke;
- manual API 26 / 30 / 36 compatibility matrix;
- a manual matrix-summary artifact combining the three Stage 23 baseline summaries.

The Stage 23 wrapper calls Stage 22 first, so the full historical IME validation chain remains intact.

## Physical-device procedure

Use the exact debug APK produced by CI. Enable USB debugging, connect one target device, confirm `adb devices` lists it, then run from the project root:

```bash
STAGE23_DEVICE_LABEL=physical-lowend \
  bash scripts/stage23_ci_real_device_baseline.sh \
  app-debug.apk \
  stage23-physical-lowend-report
```

For a second device, use a different label/output directory. If more than one ADB device is attached, set the standard `ANDROID_SERIAL` environment variable before invoking the script so ADB targets the intended device; Stage 23 itself does not write that serial into the evidence package.

Recommended physical coverage before Stage 24:

1. one low-end/minimum-supported Android device near API 26 if available;
2. one mid-range device around Android 11/API 30;
3. one current device near the target SDK/API 36;
4. five default rounds on each device, then repeat any suspicious result before treating it as a tuning signal.

## Interpretation rule

Stage 23 answers: **what does the current Stage 22 keyboard actually do on these devices?**

It does not answer: **what should the thresholds be?** That decision belongs to Stage 24 after evidence exists. Emulator numbers are useful for compatibility/regression comparison but must not be presented as equivalent to physical-device performance.

## Verification boundary

This source package prepares the collection and CI paths. If it is verified in an environment without ADB/Android emulator or a physical device, no real-device timing, memory, or frame result is claimed. The parser and source contracts can be tested offline, but actual baseline values are created only when the Stage 23 ADB script runs against a real Android target.
